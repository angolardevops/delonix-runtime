Kinds do manifesto

Cada Kind com um template COMPLETO e funcional — todos os campos, com os defaults e um comentário. Aplica um só com delonix <grupo> apply -f, ou todos de uma vez com delonix stack apply (ordem por dependência: Secret → Network → NetworkRoute → Volume → Image → VirtualMachine → Container → Pod → Ingress → NetworkPolicy → HTTPRoute → Gateway). Os antigos kind: Storage, ShareVolume e Egress foram removidos: a capacidade vive agora em blocos do Volume (nfs:/cifs:/webdav:/share:) e do NetworkPolicy (direction: egress) — aplicá-los pelo nome antigo dá erro, a apontar o substituto. A lista completa, com os grupos e o que cada documento se torna, está em Estrutura de recursos.

Each Kind with a COMPLETE, functional template — every field, with defaults and a comment. Apply just one with delonix <group> apply -f, or all at once with delonix stack apply (dependency order: Secret → Network → NetworkRoute → Volume → Image → VirtualMachine → Container → Pod → Ingress → NetworkPolicy → HTTPRoute → Gateway). The former kind: Storage, ShareVolume and Egress were removed: the capability now lives in blocks on Volume (nfs:/cifs:/webdav:/share:) and on NetworkPolicy (direction: egress) — applying them by the old name errors with the replacement. The full list, with the groups and what each document becomes, is in Resource structure.

Desde a v0.47.0 o apply converge: o stack plan diz o que mudaria e porquê, e o apply reconfigura portas, volumes, redes, memória e CPU a quente, sem mudar o PID — recusando, com o nome do campo, o que obrigaria a recriar (a não ser com --replace). Sem ficheiro de estado: o último spec aplicado vive no próprio recurso. Continua fail-fast e sem rollback, e é convergência a pedido — não um loop. Os templates abaixo são os ficheiros reais em examples/.

Since v0.47.0 apply converges: stack plan says what would change and why, and apply reconfigures ports, volumes, networks, memory and CPU hot, with the PID unchanged — refusing, by field name, anything that would need a recreate (unless you pass --replace). No state file: the last applied spec lives on the resource itself. Still fail-fast and without rollback, and still convergence on demand — not a loop. The templates below are the real files in examples/.

Secret

Um segredo do cofre cifrado em repouso. Consumido por run --secret/--secret-files e por passwordSecret do Storage. Os valores NUNCA ficam no registo do container em texto — são resolvidos no arranque a partir do NOME.

A secret from the vault, encrypted at rest. Consumed by run --secret/--secret-files and by Storage's passwordSecret. Values are NEVER kept in the container's registry as plaintext — they're resolved at startup from the NAME.

# ============================================================================
# kind: Secret — saco de pares CHAVE=valor, cifrado em repouso (ADR-0020)
# kind: Secret — a bag of KEY=value pairs, encrypted at rest (ADR-0020)
#
# PT: Um Secret guarda pares chave=valor cifrados em repouso (XChaCha20-Poly1305
#     sob a chave-mestra do host). É consumido por `Container.secret` (como env
#     ou ficheiros /run/secrets/<nome>), pelos blocos `cifs:`/`webdav:` de
#     `kind: Volume` (`passwordSecret`, que lê a chave `password`),
#     por `Image.pullSecret` e por `provision.truenas.*Secret`. É a forma
#     DECLARATIVA do `delonix secret create`, fechando o ciclo só em YAML.
# EN: A Secret holds key=value pairs encrypted at rest (XChaCha20-Poly1305 under
#     the host master key). It is consumed by `Container.secret` (as env or
#     /run/secrets/<name> files), by the `cifs:`/`webdav:` blocks of
#     `kind: Volume` (`passwordSecret`, which reads the `password` key),
#     by `Image.pullSecret` and by `provision.truenas.*Secret`. It is the
#     DECLARATIVE form of `delonix secret create`, closing the loop in YAML only.
#
# PT: Três fontes — `stringData`, `fromEnvFile`, `fromEnv` — que podem ser
#     COMBINADAS num só documento. Precedência: `fromEnvFile` primeiro, depois
#     `stringData` sobrepõe-se (o inline ganha ao ficheiro), e `fromEnv` junta-se.
#     Não há campo `data:` (base64): o motor só lê estas três.
# EN: Three sources — `stringData`, `fromEnvFile`, `fromEnv` — that can be
#     COMBINED in one document. Precedence: `fromEnvFile` first, then `stringData`
#     overrides it (inline wins over the file), and `fromEnv` adds to it. There is
#     no `data:` (base64) field: the engine only reads these three.
#
# PT: Aplicar:  delonix stack apply -f examples/core/secret.yaml
# EN: Apply:    delonix stack apply -f examples/core/secret.yaml
#   PT: Os Secrets são aplicados ANTES do que os referencia (Volume/Container/Image).
#   EN: Secrets are applied BEFORE whatever references them (Volume/Container/Image).
# ============================================================================

# ── 1. stringData — inline, cómodo para dev ─────────────────────────────────
#      stringData — inline, handy for dev
# PT: Os VALORES ficam em CLARO no ficheiro, por isso o apply imprime um aviso.
#     Serve para dev; nunca commites valores reais num repositório.
# EN: The VALUES are CLEARTEXT in the file, so the apply prints a warning.
#     Fine for dev; never commit real values to a repository.
---
apiVersion: core.delonix.io/v1alpha1
kind: Secret
metadata:
  name: nas-creds
  labels:                      # PT: rótulos livres guardados com o recurso | EN: free-form labels stored with the resource
    app: demo
  annotations:                 # PT: anotações livres | EN: free-form annotations
    delonix.io/purpose: "example only"
spec:
  stringData:
    password: change-me        # PT: a chave que `Volume.<cifs|webdav>.passwordSecret` procura | EN: the key `Volume.<cifs|webdav>.passwordSecret` looks for
    apiKey: dummy-api-key      # PT: `apiKeySecret` procura `apiKey` (ou `token`) | EN: `apiKeySecret` fields look for `apiKey` (or `token`)
    username: demo             # PT: `Image.pullSecret` quer `username` + `password` | EN: `Image.pullSecret` wants `username` + `password`

# ── 2. fromEnvFile — carregar linhas KEY=value de um ficheiro .env ───────────
#      fromEnvFile — load KEY=value lines from a .env file
# PT: Mantém os valores FORA do manifesto. Um caminho relativo resolve-se contra
#     a pasta do próprio manifesto.
# EN: Keeps the values OUT of the manifest. A relative path resolves against the
#     manifest's own folder.
---
apiVersion: core.delonix.io/v1alpha1
kind: Secret
metadata:
  name: app-env
spec:
  fromEnvFile: ./secret-source.env   # PT: ex.: DATABASE_URL=..., API_TOKEN=... | EN: e.g. DATABASE_URL=..., API_TOKEN=...

# ── 3. fromEnv (mapa) — ler do ambiente do PROCESSO, renomeando ──────────────
#      fromEnv (mapping) — read from the PROCESS environment, renaming
# PT: `<chave no secret>: <variável de ambiente a ler>`. A chave é o que o
#     consumidor procura; a variável é a que o job de CI exporta. Uma variável
#     NÃO definida é um ERRO no apply, nunca um secret vazio.
# EN: `<key in the secret>: <environment variable to read>`. The key is what the
#     consumer looks up; the variable is whatever the CI job exports. A variable
#     that is NOT set is an ERROR at apply time, never an empty secret.
---
apiVersion: core.delonix.io/v1alpha1
kind: Secret
metadata:
  name: env-map-secret
spec:
  fromEnv:
    password: EXAMPLE_DB_PASSWORD   # PT: `provision.truenas.passwordSecret` quer `password` | EN: `provision.truenas.passwordSecret` wants `password`
    token: EXAMPLE_API_TOKEN        # PT: `Gateway.tokenSecretRef` quer `token` | EN: `Gateway.tokenSecretRef` wants `token`

# ── 4. fromEnv (lista) — atalho quando chave == variável ─────────────────────
#      fromEnv (list) — shorthand when key name == variable name
---
apiVersion: core.delonix.io/v1alpha1
kind: Secret
metadata:
  name: env-list-secret
spec:
  fromEnv:
    - DATABASE_URL
    - SENTRY_DSN

# ── 5. Combinado — as três fontes num só documento ──────────────────────────
#      Combined — all three sources in one document
# PT: O ficheiro dá a base, `stringData` sobrepõe `LOG_LEVEL`, `fromEnv` junta um
#     valor lido do ambiente do processo.
# EN: The file gives the base, `stringData` overrides `LOG_LEVEL`, `fromEnv` adds a
#     value read from the process environment.
---
apiVersion: core.delonix.io/v1alpha1
kind: Secret
metadata:
  name: combined-secret
spec:
  fromEnvFile: ./secret-source.env
  stringData:
    LOG_LEVEL: debug
  fromEnv:
    - EXAMPLE_EXTRA

Pod

O schema de Pod do Kubernetes (spec.containers[]) — portas/env/resources/securityContext/volumeMounts estruturados. O MESMO schema continua aceite num kind: Container, com aviso, e não é reescrito de propósito: um kind: Container chamado web cria um container web, este cria a netns pod-web cujo membro é web-c0 — renomear um workload nas costas de quem o escreveu partiria o DNS e os backends de HTTPRoute. O MESMO ficheiro mostra também o pod REAL multi-container: N containers a partilhar netns (mesmo IP, localhost entre si), IPC e UTS, geridos com delonix pod create/ls/describe/rm/logs.

The Kubernetes Pod schema (spec.containers[]) — structured ports/env/resources/securityContext/volumeMounts. The SAME schema is still accepted on a kind: Container, with a warning, and is deliberately not rewritten for you: a kind: Container named web creates a container web, this creates the pod netns pod-web whose member is web-c0 — renaming a workload behind your back would break DNS and HTTPRoute backends. The SAME file also shows the REAL multi-container pod: N containers sharing netns (same IP, reachable via localhost), IPC and UTS, managed with delonix pod create/ls/describe/rm/logs.

# ============================================================================
# kind: Pod — N contentores que partilham um namespace de rede (ADR-0006)
# kind: Pod — N containers sharing one network namespace (ADR-0006)
#
# PT: Esquema k8s (`spec.containers[]` com ports/env/resources/securityContext
#     estruturados + `volumes[]` ao nível do pod) mais um campo `network` próprio
#     do motor. Os membros partilham o netns do pod (mesmo IP, `localhost` entre
#     si) e os namespaces IPC/UTS; `shareProcessNamespace: true` partilha também
#     o PID. Só `containers[].image` é obrigatório.
# EN: k8s schema (`spec.containers[]` with structured ports/env/resources/
#     securityContext + pod-level `volumes[]`) plus an engine-specific `network`
#     field. Members share the pod netns (same IP, `localhost` between them) and
#     the IPC/UTS namespaces; `shareProcessNamespace: true` shares PID too. Only
#     `containers[].image` is mandatory.
#
# PT: Aplicar:   delonix stack apply -f examples/compute/pod.yaml
# EN: Apply:     delonix stack apply -f examples/compute/pod.yaml
# ============================================================================

# ── 1. mínimo — só containers[].image é obrigatório ─────────────────────────
#      minimal — only containers[].image is mandatory
---
apiVersion: compute.delonix.io/v1alpha1
kind: Pod
metadata:
  name: minimal-pod
spec:
  containers:
    - image: alpine:3.20              # PT: membro sem nome => contentor "minimal-pod-c0" | EN: unnamed member => container "minimal-pod-c0"
      command: ["sleep", "infinity"]

# ── 2. recursos de apoio para os cenários abaixo ────────────────────────────
#      supporting resources for the scenarios below
---
apiVersion: networking.delonix.io/v1alpha1
kind: Network
metadata:
  name: pod-net
spec:
  driver: bridge
---
apiVersion: storage.delonix.io/v1alpha1
kind: Volume
metadata:
  name: pod-data                      # PT: referido por `persistentVolumeClaim.claimName` | EN: referenced via `persistentVolumeClaim.claimName`
spec:
  driver: local
---
apiVersion: storage.delonix.io/v1alpha1
kind: Volume
metadata:
  name: pod-cache                     # PT: referido por `source` (extensão delonix) | EN: referenced via `source` (delonix extension)
spec:
  driver: local

# ── 3. um contentor — esquema k8s com ports/env/volumes/securityContext ─────
#      single container — k8s schema with ports/env/volumes/securityContext
---
apiVersion: compute.delonix.io/v1alpha1
kind: Pod
metadata:
  name: web
  namespace: default
spec:
  network: pod-net                    # PT: host | none | <rede própria> | EN: host | none | <custom network>
  restartPolicy: Always               # PT: Always | OnFailure | Never (valores delonix também OK) | EN: Always | OnFailure | Never (delonix spellings also OK)
  expose: 80                          # PT: auto-registar esta porta HTTP no proxy L7 (opcional) | EN: auto-register this HTTP port in the L7 proxy (optional)
  hostAliases:                        # PT: entradas /etc/hosts extra, forma k8s (uma entrada por hostname) | EN: extra /etc/hosts entries, k8s shape
    - ip: 10.0.0.9
      hostnames: [legacy-api, legacy-api.internal]
  containers:
    - name: web
      image: nginx:latest
      command: ["/bin/sh", "-c"]      # PT: substitui o ENTRYPOINT (semântica k8s) | EN: overrides ENTRYPOINT (k8s semantics)
      args: ["nginx -g 'daemon off;'"]   # PT: substitui o CMD | EN: overrides CMD
      ports:
        - containerPort: 80
          hostPort: 8080              # PT: publicado só quando hostPort está posto | EN: published only when hostPort is set
          protocol: TCP
      env:
        - name: TZ
          value: UTC
      volumeMounts:
        - name: site
          mountPath: /usr/share/nginx/html
          readOnly: true
        - name: scratch
          mountPath: /tmp/cache
      resources:
        limits:
          cpu: "500m"                 # PT: 500m => 0.5 núcleos | EN: 500m => 0.5 cores
          memory: 256Mi
      securityContext:
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]
  volumes:
    - name: site
      hostPath:
        path: /srv/www                # PT: bind mount de um directório do host | EN: bind mount of a host directory
    - name: scratch
      emptyDir: {}                    # PT: efémero => tmpfs | EN: ephemeral => tmpfs

#      full multi-container — every pod-level and container field
---
apiVersion: compute.delonix.io/v1alpha1
kind: Pod
metadata:
  name: full-pod
  namespace: default                  # PT: namespace de isolamento (um pod isola como um contentor) | EN: isolation namespace (a pod is isolated like a container)
  labels:
    app: full-pod
spec:
  # ---- nível do pod / pod-level ----
  network: pod-net                    # PT: extensão delonix: rede SDN do netns partilhado do pod | EN: delonix extension: SDN network of the pod's shared netns
  restartPolicy: OnFailure            # PT: Always | OnFailure | Never (also always/on-failure/no) | EN: Always | OnFailure | Never (also always/on-failure/no)
  hostname: full-pod-host             # PT: hostname partilhado por todos os membros (default: nome do pod) | EN: hostname shared by every member (default: pod name)
  shareProcessNamespace: false        # PT: true => membros veem os processos uns dos outros (ver cenário 5) | EN: true => members see each other's processes (see scenario 5)
  hostAliases:                        # PT: entradas /etc/hosts extra em cada membro, forma k8s | EN: extra /etc/hosts entries in every member, k8s shape
    - ip: 10.0.0.9
      hostnames: [legacy-api, legacy-api.internal]
    - ip: 10.0.0.10
      hostnames: [billing]

  # ---- volumes do pod, referidos por containers[].volumeMounts[].name ----
  volumes:
    - name: site
      hostPath:                       # PT: bind mount de um directório do host | EN: bind mount of a host directory
        path: /srv/www
    - name: scratch
      emptyDir:                       # PT: efémero, apoiado por tmpfs (RAM do host) | EN: ephemeral, backed by tmpfs (host RAM)
        medium: Memory                # PT: "" avisaria: k8s significa disco do nó, este motor usa sempre tmpfs | EN: "" would warn: k8s means node disk, this engine always uses tmpfs
    - name: data
      persistentVolumeClaim:          # PT: um Volume NOMEADO (`kind: Volume`), por nome | EN: a NAMED volume (`kind: Volume`), by name
        claimName: pod-data
    - name: cache
      source: pod-cache               # PT: extensão delonix: Volume nomeado por string `source` | EN: delonix extension: named Volume by plain source string

  # ---- membros / members ----
  containers:
    - name: web                       # PT: nome do membro; o contentor chama-se <pod>-<nome> (default c<índice>) | EN: member name; container is <pod>-<name> (default c<index>)
      image: nginx:latest             # PT: OBRIGATÓRIO | EN: REQUIRED
      command: ["/bin/sh", "-c"]      # PT: `command` k8s => substitui o ENTRYPOINT | EN: k8s `command` => overrides ENTRYPOINT
      args: ["nginx -g 'daemon off;'"]   # PT: `args` k8s => substitui o CMD | EN: k8s `args` => overrides CMD
      workingDir: /usr/share/nginx/html  # PT: directório onde o processo arranca | EN: directory the process starts in
      ports:
        - containerPort: 80
          hostPort: 8080              # PT: publicado no host SÓ quando hostPort está posto | EN: published only when hostPort is set
          protocol: TCP               # PT: TCP | UDP (default TCP) | EN: TCP | UDP (default TCP)
          hostIP: 127.0.0.1           # PT: endereço de bind da porta publicada | EN: bind address of the published port
        - containerPort: 443          # PT: sem hostPort => só informativo, não publicado | EN: no hostPort => informational only, not published
      env:
        - name: TZ
          value: Africa/Luanda
        - name: LOG_LEVEL
          value: info
      volumeMounts:
        - name: site
          mountPath: /usr/share/nginx/html
          readOnly: true
        - name: scratch
          mountPath: /tmp/cache
        - name: data
          mountPath: /var/lib/web
        - name: cache
          mountPath: /var/cache/web
      resources:
        limits:                       # PT: aplicados como limites cgroup (`requests` são só indicativos) | EN: enforced as cgroup limits (`requests` advisory)
          cpu: "500m"                 # PT: 500m => 0.5 núcleos | EN: 500m => 0.5 cores
          memory: 256Mi
      securityContext:
        privileged: false
        runAsUser: 101
        readOnlyRootFilesystem: true
        capabilities:
          drop: ["ALL"]
          add: ["NET_BIND_SERVICE"]

      image: busybox:latest
      command: ["sh", "-c"]
      args: ["while true; do wget -qO- http://localhost:80/ >/dev/null 2>&1; sleep 10; done"]

          memory: 64Mi

Workload

UM objecto declarativo para os dois tipos de computação: spec.type: container | vm | pod | microvm + o bloco com o mesmo nome. Baixa para o Kind correspondente no load — não redefine um único campo, por isso não pode divergir dele.

ONE declarative object for both kinds of compute: spec.type: container | vm | pod | microvm plus the block with that same name. Lowers to the matching Kind on load — it doesn't redefine a single field, so it can never drift from it.

# ============================================================================
# kind: Workload — UM objecto declarativo para todo o tipo de compute (ADR-0001/0006)
# kind: Workload — ONE declarative object for every compute type (ADR-0001/0006)
#
# PT: Um Workload é açúcar: NÃO sobrevive ao load — é reescrito no Kind alvo e
#     flui pelo apply normal desse Kind. `spec.type` escolhe o alvo e o bloco com
#     o nome do type carrega EXACTAMENTE o spec desse Kind (nada é redefinido):
#       type: container -> spec.container == kind: Container     (compute/container.yaml)
#       type: vm        -> spec.vm        == kind: VirtualMachine (compute/virtualmachine.yaml)
#       type: pod       -> spec.pod       == kind: Pod           (compute/pod.yaml)
#       type: microvm   -> spec.microvm   == kind: VirtualMachine, backend FORÇADO a cloud-hypervisor
#     Exactamente UM bloco, o que casa com `type` (qualquer outro é erro). O
#     `metadata` (name/namespace/labels/annotations) é herdado pelo recurso baixado.
# EN: A Workload is sugar: it does NOT survive the load — it is rewritten into the
#     target Kind and flows through that Kind's normal apply. `spec.type` picks
#     the target and the block named after the type carries EXACTLY that Kind's
#     spec (nothing is redefined):
#       type: container -> spec.container == kind: Container     (compute/container.yaml)
#       type: vm        -> spec.vm        == kind: VirtualMachine (compute/virtualmachine.yaml)
#       type: pod       -> spec.pod       == kind: Pod           (compute/pod.yaml)
#       type: microvm   -> spec.microvm   == kind: VirtualMachine, backend FORCED to cloud-hypervisor
#     Exactly ONE block, the one matching `type` (any other is an error). The
#     `metadata` (name/namespace/labels/annotations) is inherited by the lowered resource.
#
# PT: Aplicar:   delonix stack apply -f examples/compute/workload.yaml
#     Ver o que baixa:  delonix stack apply --dry-run -f examples/compute/workload.yaml
# EN: Apply:     delonix stack apply -f examples/compute/workload.yaml
#     See what it lowers to:  delonix stack apply --dry-run -f examples/compute/workload.yaml
# ============================================================================

# ── 1. recursos de apoio para os cenários abaixo ────────────────────────────
#      supporting resources for the scenarios below
---
apiVersion: networking.delonix.io/v1alpha1
kind: Network
metadata:
  name: wl-net
spec:
  driver: bridge
---
apiVersion: core.delonix.io/v1alpha1
kind: Secret
metadata:
  name: wl-secret
spec:
  stringData:
    API_TOKEN: example-token-not-real
---
apiVersion: storage.delonix.io/v1alpha1
kind: Volume
metadata:
  name: wl-data
spec:
  driver: local

# ── 2. type: container — o spec de Container plano, todos os campos ──────────
#      type: container — the flat Container spec, every field
---
apiVersion: compute.delonix.io/v1alpha1
kind: Workload
metadata:
  name: wl-container

Dependency

Alcançabilidade DIRIGIDA entre containers (ao contrário da rede, que é bidireccional): from alcança to, e to não fica exposto aos outros. É açúcar reduzido no load para kind: NetworkPolicy — sem dataplane novo. Várias dependências para o mesmo alvo ACUMULAM os allows (por isso são fundidas por alvo, e não uma política por dependência).

DIRECTED reachability between containers (unlike a network, which is bidirectional): from reaches to, and to stays unexposed to the others. Sugar lowered on load into kind: NetworkPolicy — no new dataplane. Several dependencies on the same target ACCUMULATE their allows, which is why they are merged by target rather than one policy per dependency.

# ============================================================================
# kind: Dependency (alias: KnowDepends) — alcançabilidade DIRIGIDA entre containers
# kind: Dependency (alias: KnowDepends) — DIRECTED reachability between workloads
#
# PT: Ao contrário de uma Network (bidireccional), abre UM sentido: `from` alcança
#     `to`, mas `to` NÃO inicia para `from` — e `to` deixa de ficar exposto a todos
#     os outros na rede. Caso clássico: a app conhece a DB, a DB não conhece a app.
#     É AÇÚCAR: no load cada Dependency é reescrita para um `kind: NetworkPolicy`
#     com `direction: ingress` no `to` (default-deny + um allow por `from`, nomeando
#     o peer por WORKLOAD para sobreviver a restarts). Várias Dependency para o
#     mesmo `to` acumulam e fundem-se numa só política. Corre
#     `delonix stack apply --dry-run` para ver a política real.
# EN: Unlike a Network (bidirectional), it opens ONE direction: `from` reaches `to`,
#     but `to` does NOT initiate towards `from` — and `to` stops being exposed to
#     everyone else on the network. Classic case: the app knows the DB, the DB does
#     not know the app. It is SUGAR: at load each Dependency is rewritten into a
#     `kind: NetworkPolicy` with `direction: ingress` on `to` (default-deny + one
#     allow per `from`, naming the peer by WORKLOAD so it survives restarts). Several
#     Dependencies for the same `to` accumulate and merge into one policy. Run
#     `delonix stack apply --dry-run` to see the real policy.
#
# PT: Campos spec: from (obrigatório, string), to (string ou lista), ports (lista),
#     proto. A regra nomeia o peer por workload, não por IP — o endereço de um
#     container vem da SDN e muda num restart.
# EN: spec fields: from (required, string), to (string or list), ports (list), proto.
#     The rule names the peer by workload, not by IP — a container's address comes
#     from the SDN and changes on a restart.
#
# PT: Aplicar:  delonix stack apply -f examples/networking/dependency.yaml
# EN: Apply:    delonix stack apply -f examples/networking/dependency.yaml

NetworkRoute

O grau ACIMA do Dependency: aquele liga dois WORKLOADS, este liga duas REDES — isoladas por omissão. Uma rota diz que o pacote PODE atravessar; nunca diz que é PERMITIDO — quem decide isso continua a ser o FirewallPolicy/Dependency em cada extremidade. São duas perguntas em série (há caminho? → é aceite?), por isso são dois Kinds e não um campo routes: dentro de Network. Dirigida (from inicia, o retorno flui; to nunca inicia de volta); custo constante, não cresce com o número de redes.

The grade ABOVE Dependency: that one links two WORKLOADS, this one links two NETWORKS — isolated by default. A route says the packet CAN cross; it never says it's ALLOWED — that decision still belongs to FirewallPolicy/Dependency at each end. Two questions in series (is there a path? → is it accepted?), which is why they're two Kinds and not one routes: field inside Network. Directed (from initiates, the return flows; to never initiates back); constant cost, doesn't grow with the number of networks.

# ============================================================================
# kind: NetworkRoute — caminho DIRIGIDO entre duas REDES (ADR-0013 tier B)
# kind: NetworkRoute — a DIRECTED path between two NETWORKS (ADR-0013 tier B)
#
# PT: As redes são isoladas por omissão. Isto declara que uma PODE alcançar a
#     outra — dirigido, como `kind: Dependency` entre containers: `from` inicia e
#     o retorno flui (established); `to` NÃO inicia de volta. O spec tem EXACTAMENTE
#     dois campos, `from` e `to` — não há `via`. A identidade é o PAR (from->to),
#     não o metadata.name; dois documentos para o mesmo par são recusados.
# EN: Networks are isolated by default. This declares that one MAY reach the other
#     — directed, like `kind: Dependency` between containers: `from` initiates and
#     the return flows (established); `to` does NOT initiate back. The spec has
#     EXACTLY two fields, `from` and `to` — there is no `via`. Identity is the PAIR
#     (from->to), not metadata.name; two documents for the same pair are refused.
#
# PT: Uma rota diz que o pacote PODE atravessar; nunca que é PERMITIDO. A política
#     por-workload (NetworkPolicy/Dependency) continua a decidir. São duas perguntas
#     em série — por isso dois Kinds: NetworkRoute (há caminho?) e depois a política

# EN: A route says the packet MAY cross; never that it is ALLOWED. Per-workload

Stack

Agrupa vários recursos num só documento. Expandido no load para os Kinds individuais, em ordem de dependência — o Stack não sobrevive ao load, tudo o resto vê os filhos.

Groups several resources into one document. Expanded on load into the individual Kinds, in dependency order — the Stack doesn't survive the load, everything else sees the children.

# ============================================================================
# kind: Stack — agregado que agrupa uma app inteira num só documento
# kind: Stack — the aggregate that groups a whole app in one document
#
# PT: Um Stack reúne redes, contentores, volumes, … (à maneira de um
#     k8s-Service). Ao carregar, expande-se nos recursos constituintes, que
#     seguem o apply normal por-Kind EM ORDEM DE DEPENDÊNCIA (a ordem que
#     `delonix stack plan --fields` imprime — a ordem da tabela de Kinds, não uma
#     lista mantida aqui). Cada filho herda o namespace do Stack salvo se definir
#     o seu, e pode levar `labels:`/`annotations:` ao lado de `name:`. Um item de
#     grupo é `{ name, namespace?, labels?, annotations?, spec }`: `spec` é
#     exactamente o `spec` do Kind que o grupo representa.
# EN: A Stack bundles networks, containers, volumes, … (k8s-Service-like). At load
#     time it expands into its constituent resources, which then flow through the
#     normal per-Kind apply IN DEPENDENCY ORDER (the order `delonix stack plan
#     --fields` prints — the order of the Kind table, not a list kept here). Each
#     child inherits the Stack's namespace unless it sets its own, and can carry
#     `labels:`/`annotations:` next to `name:`. A group item is
#     `{ name, namespace?, labels?, annotations?, spec }`: `spec` is exactly the
#     `spec` of the Kind the group stands for.
#
# PT: Este exemplo usa TODOS os grupos que um Stack aceita (o teste
#     `the_stack_example_names_every_group` falha se faltar um), por isso serve de
#     referência de como cada um se parece. Para um Kind sozinho com todas as suas
#     opções, ver examples/full-<kind>.yaml.
# EN: This example uses EVERY group a Stack accepts (the test
#     `the_stack_example_names_every_group` fails if one is missing), so it doubles
#     as the reference for what each one looks like. For a single Kind with all of
#     its options, see examples/full-<kind>.yaml.
#
#   grupo / group        Kind               referência / reference
#   runtimePolicies      RuntimePolicy      full-runtimepolicy.yaml
#   secrets              Secret             core/secret.yaml
#   networks             Network            full-network.yaml
#   networkRoutes        NetworkRoute       full-networkroute.yaml
#   networkZones         NetworkZone        networkzone.yaml
#   storagePools         StoragePool        full-volume.yaml
#   volumes              Volume             full-volume.yaml
#   objectStorages       ObjectStorage      storage/objectstorage.yaml
#   images               Image              full-image.yaml
#   apps                 App                full-app.yaml
#   vms                  VirtualMachine     full-virtualmachine.yaml
#   systemContainers     SystemContainer    systemcontainer.yaml
#   containers           Container          full-container.yaml
#   pods                 Pod                full-pod.yaml
#   services             Service            full-service.yaml
#   ingress              Ingress            full-ingress.yaml
#   firewallPolicies     NetworkPolicy      full-networkpolicy.yaml
#   networkAccessRules   NetworkAccessRule  full-networkaccessrule.yaml

#
# PT: `tunnels:` é a grafia antiga de `gateways:` e ainda carrega. Não agrupáveis:
#     `Stack` (não encaixa noutro) e `KubernetesCluster` (procedimento remoto por
#     SSH, não um recurso deste nó — ver full-kubernetescluster.yaml).
# EN: `tunnels:` is the old spelling of `gateways:` and still loads. Not groupable:
#     `Stack` (does not nest) and `KubernetesCluster` (a remote procedure over SSH,
#     not a resource of this node — see full-kubernetescluster.yaml).
#
# PT: Aplicar:  delonix stack apply -f examples/core/stack.yaml
# EN: Apply:    delonix stack apply -f examples/core/stack.yaml

#      The blog Stack — one document naming every group

  #     re-aplicar deixa policy.json intacto; `delonix policy unset` é a única descida.

  # PT: Armazenamento de objectos S3 (ver storage/objectstorage.yaml). `cephRgw`

    - name: media

        bucket: media

          endpoint: http://rgw.internal:80

    - name: alpine-base
      spec:
        pull: alpine:3.20  # PT: `pull` e `build` são alternativas; ver full-image.yaml | EN: `pull` and `build` are alternatives; see full-image.yaml

  # EN: Cloud Native Buildpacks: source in, image out (see full-app.yaml).
  apps:
    - name: shop
      spec:
        source: .
        image: shop:1.0           # PT: com tag, não :latest — a runtimePolicy acima nega :latest | EN: tagged, not :latest — the runtimePolicy above denies :latest

  # PT: Um microVM/VM na mesma SDN. Precisa de imagem ou disco de VM no host para aplicar.

  #     motor puxa a imagem; memória/swap/cores mudam em sítio, o resto recria (ADR-0058).

  #     provider (today: a Proxmox node, via DELONIX_PROXMOX_URL), never named here.

    - name: web

        containers:
          - name: app

  # PT: DNS round-robin sobre cada contentor que o selector casa, sob

KubernetesCluster

Bootstrap kubeadm idempotente sobre hosts JÁ vivos, por SSH. Sem ficheiro de estado: cada passo tem um check, por isso nunca dessincroniza. Ver também cluster-vm.yaml (provisiona as VMs) e cluster-kind.yaml (modo kind).

Idempotent kubeadm bootstrap on hosts that are ALREADY alive, over SSH. No state file: every step has a check, so it can never drift. See also cluster-vm.yaml (provisions the VMs) and cluster-kind.yaml (kind mode).

# ============================================================================
# kind: KubernetesCluster — um cluster kubeadm em três modos (um por documento)
# kind: KubernetesCluster — a kubeadm cluster in three modes (one per document)
#
# PT: `spec.mode` é o discriminador e cada modo lê só o seu bloco:
#       kind  → nós em containers, NESTA máquina (sem Docker, sem o binário kind)
#       vm    → cada nó é uma microVM real da imagem dourada (isolamento de hipervisor)
#       ssh   → hosts remotos que JÁ EXISTEM (bare-metal ou VMs de outrem)
#     Os campos comuns (k8sVersion/podSubnet/serviceSubnet/cni) são partilhados;
#     os específicos vivem no bloco do modo (`kind:`, `vm:`, `ssh:`).
# EN: `spec.mode` is the discriminator and each mode reads only its own block:
#       kind  → nodes as containers, on THIS machine (no Docker, no `kind` binary)
#       vm    → every node is a real microVM from the golden image (hypervisor isolation)
#       ssh   → remote hosts that ALREADY EXIST (bare metal or someone else's VMs)
#     The common fields (k8sVersion/podSubnet/serviceSubnet/cni) are shared; the
#     specific ones live in the mode's block (`kind:`, `vm:`, `ssh:`).
#
# PT: FORA do ciclo do stack. Um cluster NÃO é um recurso do nó — é um
#     procedimento remoto por SSH. Por isso este Kind NÃO entra em
#     `stack apply`/`--prune`/`destroy`. Aplica-se com o seu próprio comando:
#       delonix cluster apply   -f examples/cluster/kubernetescluster.yaml
#     e valida-se offline (sem tocar em máquina nenhuma) com:
#       delonix stack validate  -f examples/cluster/kubernetescluster.yaml
#       delonix manifest validate -f examples/cluster/kubernetescluster.yaml

#       delonix cluster apply   -f examples/cluster/kubernetescluster.yaml
#     and validate it offline (touching no machine) with:
#       delonix stack validate  -f examples/cluster/kubernetescluster.yaml
#       delonix manifest validate -f examples/cluster/kubernetescluster.yaml

NetworkPolicy (as duas direcções)

Firewall L4 declarativo por direcção (estilo k8s NetworkPolicy; o nome antigo FirewallPolicy continua aceite como alias). Cada documento é o estado desejado de UMA direcção de um container-alvo — allowlist + default-deny, idempotente. O kind: Egress deixou de existir: é direction: egress nesta mesma política (partilhavam a struct inteira). Duas políticas para o mesmo par (alvo, direcção) são RECUSADAS — a segunda apagaria as regras da primeira com ambas a dizer que correu bem.

Declarative per-direction L4 firewall (k8s NetworkPolicy-style; the old name FirewallPolicy is still accepted as an alias). Each document is the desired state of one direction for one target container — allowlist + default-deny, idempotent. The kind: Egress no longer exists: it is direction: egress in this same policy (they shared the whole struct).

#     deixando a outra intacta — por isso dois documentos para o mesmo
#     (alvo, direcção) são recusados. `scope: container` (default) actua num
#     workload; `scope: network` é uma política de SAÍDA de uma rede inteira

#     Só actua em workloads numa rede SDN custom.
# EN: Direction is `spec.direction` (ingress|egress) and reach is `spec.scope`.
#     Each document is the DESIRED STATE of ONE direction of ONE target: applying
#     it REPLACES that direction's rules (allowlist + default), leaving the other
#     untouched — so two documents for the same (target, direction) are refused.
#     `scope: container` (default) acts on a workload; `scope: network` is a whole

# kind: HTTPRoute — reverse-proxy L7/HTTP declarativo (estilo Gateway API)
# kind: HTTPRoute — declarative L7/HTTP reverse proxy (Gateway API style)
#
# PT: Roteia por Host e/ou prefixo de path para containers backend. O proxy
#     (hyper embutido) corre DENTRO do netns do holder — alcança os backends pelo
#     IP interno da SDN — e publica as portas de entrada no host. O TLS termina no
#     proxy (self-signed por omissão, ou um par PEM de um `kind: Secret`). TODOS
#     os documentos HTTPRoute (e Ingress) do manifesto compõem UM só proxy: os
#     listeners juntam-se por porta (TLS ganha na colisão), as rotas concatenam-se
#     e há UM único certificado (sem SNI). `kind: Ingress` é a forma k8s do MESMO
#     proxy (Compat→HTTPRoute, ver ingress.yaml); o firewall L4 é `kind:
