项目结构

阅读之前：克隆、构建与测试 —— 你已经有一份能构建的 checkout，也知道 有哪些门禁存在。

本页是这个仓库的地图：每一个顶层文件和目录是什么、谁在什么时候改动它，以及哪些部分是生成 的、绝不能手动编辑。请在读完克隆、构建与测试之后、架构 之前读本页——架构解释的是为什么代码是这样切分的；本页告诉你的是东西在哪里。读完之后， 你就能在这个仓库中给任何一个路径定位、说出是谁在改它，也知道你能不能手动编辑它，还是必须重新 生成它。

一个 CI 门禁会保证它诚实：当一个被追踪的顶层路径（或者 crates/、bins/、docs/ 的一个 二级目录）在下面的表格中缺失，或者一张表格提到了一个已经不存在的路径时， python3 scripts/dev_docs.py --check 会失败。

五分钟读懂本仓库#

从根目录开始，沿着依赖关系往里走：

  1. Cargo.toml —— workspace 本身：每一个成员 crate，以及每一个依赖的版本（成员 crate 只写 { workspace = true }）。
  2. bins/delonix-runtime-bin/src/main.rs —— delonix CLI。每一个命令组都是 src/cmd/ 下的一个模块；跟着你关心的那个组走就行。
  3. crates/<层>/<crate>/src/lib.rs —— 引擎本身。目录就是层 （foundation → contexts → adapters / providers → interfaces），每一个 lib.rs 开头都有 一段 //! 注释说明这个 crate 是做什么的。各个 crate 每个 crate 都有独立的 一节。
  4. docs/dev/ —— 本手册。docs/adr/ —— 结构背后的那些决策。

AGENTS.md 是这个项目那份又长、又用葡萄牙语写的工作日志。它有用之处在于帮你找到该去哪里 看，但其中一部分内容已经过时；它说的东西要在代码里确认一遍。

顶层文件#

路径 是什么 谁在什么时候改它 延伸阅读
Cargo.toml workspace 的根：成员列表、[workspace.package]、[workspace.dependencies]（每个 crate 的路径和每个外部依赖的版本）以及 [workspace.lints.clippy]。它的 version 就是已发布的 tag。 任何新增 crate 或依赖的人；version 只在一次发布提交里改变（scripts/version_gate.py）。 编码约定、贡献流程
Cargo.lock 整个 workspace 已解析的依赖图；构建使用 --locked。 依赖变化时由 cargo 更新；随那次变化一起提交它。 克隆、构建与测试
rust-toolchain.toml 固定带 rustfmt 和 clippy 的 Rust 频道，使开发环境与 CI 用同一个编译器构建。 维护者，在一次专门的提交里改动。 准备你的环境
buf.yaml buf v2 的配置：proto/ 模块（要 lint）和被 vendor 进来的 third_party/googleapis 模块（不 lint），附带写明的 lint 例外。 改动节点契约规则的人。 docs/adr/0040-engine-restructuring-layers-ports-node-contract.md
deny.toml cargo-deny 的策略：advisory（每一条 ignore 都附带理由）、许可证、来源。由 CI 的 cargo-deny 作业运行。 任何新增了会触发它的依赖的人——附带一段写明的理由。 克隆、构建与测试
Makefile 便捷目标：binaries（release 版的 delonix + delonix-cri，主要制品）、image、ghcr-push、bench、coverage。 维护者。 克隆、构建与测试
Delonixfile 次要 CLI 容器镜像的多阶段构建（从源码构建 delonix + delonix-cri）。 维护者，镜像构建方式变化时。 Delonixfile 与 VMfile
.dockerignore 让 target/、dist/ 和 .git 不进入 Delonixfile 的构建上下文。 很少改动。 —
.gitignore 忽略 target/、__pycache__/ 和本地的 agent 工具文件。 很少改动。 —
.git-blame-ignore-revs git blame 应该跳过的提交（那次全 workspace 的 rustfmt 运行）。用 git config blame.ignoreRevsFile .git-blame-ignore-revs 启用。 落地一次大规模重排版提交的人。 —
AGENTS.md 项目日志与 agent 规则，用葡萄牙语写成：引擎的身份与边界（权威版本）、各个门禁，以及每个功能的一段长历史。有些章节已经过时。 维护者和贡献者用来记录决策和发现；冲突用「两边都保留」的方式解决。 从这里开始
ARCHITECTURE.md C4 模型（context、containers、components）与功能性系统设计，用葡萄牙语写成，渲染进用户站点。 手写，随结构性变化与代码保持同步。 架构
README.rst 面向用户的入口：Delonix 是什么、如何安装、第一批命令。 随用户可见的功能和发布而改动。 发布文档
CONTRIBUTING.md 简短的贡献者入口，指向 docs/dev/。 手册维护者。 贡献流程
GOVERNANCE.md 决策是怎么做出来的（单一维护者模式，结构性决策用 ADR）。 维护者。 docs/adr/README.md
MAINTAINERS.md 谁维护哪个领域（今天只有一位维护者）。 维护者。 GOVERNANCE.md
CODE_OF_CONDUCT.md Contributor Covenant。 维护者。 —
SECURITY.md 如何私下报告一个漏洞（GitHub 的私有漏洞报告功能）。 维护者。 docs/SECURITY-RELEASES.md
LICENSE 项目的 Apache-2.0 许可证。 实际上从不改动。 —
.clinerules 给 Cline 助手用的指针文件：「规则在 AGENTS.md 里」。它记的 crate 数量已经过时；权威版本是 AGENTS.md 和各个 crate。 很少改动。 —
.cursorrules 给 Cursor 用的同一份指针。 很少改动。 —

源代码（crates/、bins/、proto/、tests/）#

crate 列表、每个 crate 所在的层，以及谁依赖谁，这些都是生成出来的事实，写在 架构和各个 crate里；此处不再重复。

路径 是什么 谁在什么时候改它 延伸阅读
crates/ 所有的库 crate，每层一个目录（ADR-0040）。scripts/arch_fitness.py 会让一个目录与其 LAYERS 表中声明的层不一致的 crate失败，也会让任何违反允许方向的依赖失败。 每一个引擎功能。 架构
crates/foundation/ 纯粹的基础层：只有数据的模型——错误、纯数据记录（Status、防火墙相关的记录）、secret 模型、生成的名称、退出码与 DX_* 类别（delonix-model），以及零依赖的网络规则（delonix-net-rules）。只依赖基础层本身。 新增一个共享类型或纯规则的改动。 各个 crate
crates/contexts/ 带用例的限界上下文：Compute，带着 Container 和 Vm 记录（delonix-compute），节点自己的辅助功能——事件日志、宿主机与进程检查、服务器分发（delonix-node）——，Stack——Kind、协调器、revision（delonix-stack）——，以及节点的安全决策（delonix-security-runtime）。 改变引擎决策方式的功能。 各个 crate
crates/adapters/ 这个节点上的各种机制：Linux 命名空间/cgroup（delonix-linux）、OCI 镜像（delonix-oci）、网络与防火墙（delonix-sdn）、微虚拟机（delonix-vm）、卷（delonix-volume）、持久化状态与 secret 保险库（delonix-state）、漏洞扫描（delonix-scanner）、日志/指标/追踪（delonix-telemetry）。 触碰内核、磁盘或本地工具的功能。 各个 crate、云原生入门
crates/providers/ 端口背后的远程系统：作为 VmBackend 的一个 Proxmox VE 节点（delonix-proxmox），以及 TrueNAS 的资源制备（delonix-truenas）。 对某个 provider 集成的改动；一个新 provider 以端口实现的形式进入这里。 docs/adr/0008-proxmox-vm-backend.md
crates/interfaces/ 暴露引擎的服务器：Kubernetes CRI（delonix-cri，同时也提供 delonix-cri 这个二进制程序）、本地管理 API（delonix-mgmt）以及 MCP 服务器（delonix-mcp）。 对这几种协议之一的改动。 云原生标准
bins/ 二进制 crate。每一个只组合一个接口（由 arch_fitness.py 强制执行）。 每一个 CLI 可见的功能。 架构
bins/delonix-runtime-bin/ delonix CLI：src/main.rs、src/cmd/ 下每个命令组一个模块、葡萄牙语消息目录 data/pt.po、templates/ 下的 init 项目模板、build.rs，以及 tests/architecture.rs。 每一个带命令、flag 或消息的功能。 编码约定
bins/delonix-mgmt-bin/ delonix-mgmt 二进制程序：一个覆盖在 delonix-mgmt 之上的很薄的 main.rs。 很少改动；逻辑活在接口层的那个 crate 里。 各个 crate
bins/delonix-mcp-bin/ delonix-mcp 二进制程序：一个覆盖在 delonix-mcp 之上的很薄的 main.rs。 很少改动；逻辑活在接口层的那个 crate 里。 docs/adr/0025-mcp-local-ai-control-surface.md
proto/ 节点契约 delonix.node.v1（proto/delonix/node/v1/*.proto），标记为 draft；是 gRPC 和 HTTP/JSON 以及 docs/api/openapi.yaml 的唯一真相来源。由 scripts/contract_gate.py 检查（格式、lint、破坏性变更、HTTP 映射、OpenAPI）。 契约变更，需要仔细评审——相对于上一个 tag 的破坏性变更会失败。 proto/README.md、ADR-0040
tests/ 树外的兼容性检查，不是 cargo 测试：tests/compat/cri-conformance.sh（critest 套件）和 tests/compat/docker_api_smoke.py。Cargo 的集成测试活在每个 crate 自己的 tests/ 里。 从事 CRI 或 Docker API 兼容性工作的人。 docs/cri-conformance.md、克隆、构建与测试
fuzz/ cargo-fuzz 的目标，针对喂入不受信输入（一个被克隆仓库的 Dockerfile、一个镜像引用字符串）的手写解析器。它有自己独立的 [workspace]，这样 sanitizer 的构建 flag 就永远不会碰到主 workspace；CI 的 fuzz 作业每次 push/PR 对每个目标跑 60 秒。 任何为外部可控输入新增手写解析器的人。 docs/roadmap/13-improvements-traceability.md 的 M04

文档（docs/……）#

docs/ 同时也是 GitHub Pages 的根目录。它的顶层文件是混合的：HTML 页面 （index.html、cheatsheet.html、estrutura.html……）和 .nojekyll 是由 docs/gen.py 生成的；gen.py 本身，以及像 cli-stability.md、gitops.md、estrutura.md、 guia-vm-lab.md 这样的 Markdown，是它渲染所依据的手写源文件；RELEASES.md 是由 scripts/gen-releases.sh 生成的；而带日期的报告（AUDITORIA-E2E.md、 RELATORIO-PRE-PRODUCAO.md、paridade-docker-podman.md、comparacao-medida.md、 sovereignty-engine.md）记录的是在某个特定日期测量到的结果。

路径 是什么 谁在什么时候改它 延伸阅读
docs/ 文档根目录，也是用户站点（见上面那段）。 用户可见的改动要用 python3 docs/gen.py 重新生成站点；如果已提交的 docs/ 和重新生成出来的不一样，CI 会失败。 发布文档
docs/adr/ 架构决策记录（Architecture Decision Records），NNNN-title.md，索引在 docs/adr/README.md 里。已接受的 ADR 从不重写——由一份新 ADR 取代。 提出一项结构性决策的贡献者。 docs/adr/README.md、贡献流程
docs/api/ openapi.yaml，由 protoc-gen-openapi 从 proto/ 生成。绝不要手动编辑它。 proto/ 变化之后运行 python3 scripts/contract_gate.py --update。 proto/README.md
docs/comandos/ 每个 CLI 命令组一个 HTML 页面，由 docs/gen.py 从 release 二进制程序真实的 --help 加上生成器里的编辑说明文字生成。 从不手动改：改 docs/gen.py，重新构建二进制程序，重新生成。 发布文档
docs/dev/ 本贡献者手册：英文 Markdown 源文件，带 pt-AO/ 和 fr-FR/ 翻译，翻译带有 translated-from 哈希。dev-docs:begin/dev-docs:end 标记之间的区域由 scripts/dev_docs.py 生成；其余部分是手写的。 手册维护者；生成的区域跟随代码变化，在发布时刷新。 发布文档
docs/providers/ capability-matrix.md，声明式的 provider 能力矩阵（ADR-0050），由 delonix provider matrix 生成；delonix-runtime-bin 里有一个测试，在它与实际输出不一致时会失败。 一个声明变化之后运行 delonix provider matrix > docs/providers/capability-matrix.md。 docs/adr/0050-libvirt-linux-providers-capability-catalog.md
docs/discovery/ 编号、带日期的调查与计划（清单、附带原始结果文件的 spike）。历史记录——不要重写；写一份新的。 在结构性变化之前进行调查的人。 docs/adr/
docs/handbook/ 本手册作为一个网站（en/、pt-AO/、fr-FR/、zh-CN/、index.html），由 scripts/dev_docs_site.py 从 docs/dev/ 生成。绝不要编辑 HTML。 docs/dev/ 变化之后、以及发布时，用 python3 scripts/dev_docs_site.py 重新生成。 发布文档
docs/proxmox/ Proxmox VE 的 API 覆盖矩阵（ADR-0049）：api-<ver>.routes.json，从某个节点的 apidoc.js 中提取出的一个命名版本的 schema，附带其溯源信息（抓取日期、sha256），以及 matrix-<ver>.md，由它以及 provider crate 调用的路由生成。绝不要编辑这份矩阵。 一条路由加进 delonix-proxmox 之后运行 python3 scripts/proxmox_api_inventory.py docs/proxmox/api-9.2.2.routes.json --markdown > docs/proxmox/matrix-9.2.2.md；schema 只在测量了一个新版本时才更新。 docs/adr/0049-proxmox-api-coverage-measured-matrix-not-a-cluster-proxy.md
docs/releases/ 发布说明，每个发布一份 v<version>.md。一次发布提交必须自己新增一份（version_gate.py）。历史记录——不要重写过去的说明。 发布提交本身。 贡献流程
docs/roadmap/ 一个改进项目的可追溯性矩阵，其中每一个单元格都引用了一次测量，或者写着「未测量」。 维护者，随着条目被测量或关闭。 —
docs/runtime/ 带日期的运行时调查（现状、crate 依赖图、目标与现实的对比）。历史记录：里面的 crate 名称是后来重命名之前的。 不再更新；被架构和各个 crate取代。 架构
docs/schema/ v1/delonix.json，清单的 JSON Schema，从代码生成（ADR-0007）。 一个清单类型变化时运行 delonix manifest schema > docs/schema/v1/delonix.json。 docs/adr/0007-generated-manifest-schema.md

工具、CI 与打包（scripts/、.github/、dist/、editors/、examples/、reports/、third_party/、.ai/）#

路径 是什么 谁在什么时候改它 延伸阅读

一个新文件该放在哪里？#

  • 任何层都能引用、且不涉及 I/O 的一个类型或规则 → crates/foundation/。纯粹的网络数学去 delonix-net-rules；只有数据的记录和名称去 delonix-model。
  • 一个决策或用例（该运行什么、一个 Kind 意味着什么、一份 plan） → crates/contexts/。
  • 调用内核、磁盘或本地工具（ip、nft、qemu-img）的代码 → crates/adapters/，放进 拥有那个机制的那个 crate 里。
  • 与一个远程系统的集成 → 在 crates/providers/ 里新增一个端口实现，绝不要在已有代码里 写一个 if provider == ……。
  • 一个新的协议服务器 → crates/interfaces/，由 bins/ 里恰好一个二进制程序去组合它。
  • 一个 CLI 命令或 flag → bins/delonix-runtime-bin/src/cmd/ 下的一个模块，附带它在 data/pt.po 里的葡萄牙语翻译。
  • 一个新 crate → 它所在层的目录，同时在同一次提交里，把它加进 scripts/arch_fitness.py 的 LAYERS 表和 Cargo.toml 的 [workspace.dependencies] 里。
  • 一份示例清单 → examples/（CI 会 dry-run 它）。一项结构性决策 → docs/adr/。 贡献者文档 → docs/dev/。

这份清单背后的规则，附带例子，在 编码约定 —— 结构：代码该放在哪里和各个 crate里。
