概览

Delonix Runtime — 贡献者手册

本手册面向想要修改引擎的人：你今天克隆了本仓库，想在不破坏你的宿主机或引擎的前提下发出第一个 pull request。读完本页后，你会知道本手册的编排顺序，以及针对你的角色应按什么顺序阅读哪些页面。如果你只想 使用 Delonix，请改为从 README 和 用户文档网站 开始。

工作区共有 25 个 crate，产出 5 个二进制（delonix, delonix-cri, delonix-mcp, delonix-mgmt, delonix-node-api）。

引擎是什么——以及它不是什么#

Delonix Runtime 是单个节点上的执行抽象：它运行容器和微虚拟机（microVM）， 并管理它们所需的网络和存储。它是声明式的（拥有自己的 Kind，按 apiVersion 分组——见 delonix api-resources），并且只通过端口（port）与各 provider （Linux 内核、libvirt、Cloud Hypervisor、Proxmox VE、Kubernetes 的 CRI）通信，绝不会在代码中 散布 if provider == … 这样的分支。

几乎每一条你会收到的评审意见，都由以下三条原则塑造：

  • 云原生（Cloud native） —— plan / apply / drift（偏差），API 优先（CLI、节点 API、CRI 和 MCP 服务器暴露相同的操作），通过开放标准实现可观测。
  • 无守护进程（Daemonless） —— 默认不驻留任何进程。必须持久化的东西属于 systemd， 或者属于一个有明确归属者的按工作负载（per-workload）进程。新增一个守护进程需要一份 ADR。
  • 无根优先（Rootless-first） —— 正常路径在没有 root 权限下运行；特权是显式的可选项（opt-in）。

还有一条由 CI 门禁（gate）强制的边界：引擎不认识任何消费者。 它不知道是谁在调用它， 也没有租户、账户、方案（plan）或计费的概念。来自某个消费者的需求，要么以通用引擎能力的形式进入， 要么就不进入。权威文本是 AGENTS.md 顶部的 «Identidade e fronteira do motor»（引擎的身份与边界）一节。

两个部分：生成的事实与叙述#

本手册中的页面混合了两类内容：

  • 事实（Facts） —— 存在哪些 crate、它们所处的层、谁依赖谁、有哪些二进制文件、锁定的 工具链、CI 作业。它们存在于 <!-- dev-docs:begin <key> --> 和 <!-- dev-docs:end <key> --> 标记之间，由 python3 scripts/dev_docs.py 从 Cargo.toml、scripts/arch_fitness.py、rust-toolchain.toml 和 .github/workflows/ci.yml 生成。绝不要手工编辑它们——CI 会运行 dev_docs.py --check 并使其失败。如果某个事实有误，请修正源头或生成器。
  • 叙述（Narrative） —— 事情为何如此、各个流程如何运作、如何贡献。它是手写的， 并在每次发布后接受复核。见发布文档。

本手册的组织方式#

各页面构成一门课程，从头到尾阅读。每一页开头都有一行 阅读之前， 列出它所假设你已读过的前置页面；结尾则有一行 下一步，指向承接它的页面。 站点侧栏中页面旁显示的数字，就是它在此顺序中的位置。页面内部的章节编号（例如 Rust 入门中的 §3.8，或标准页面中的 13.4）是为链接保持稳定的本地标签；它们不是页面位置。

按角色划分的阅读路径#

没有人需要在第一次改动之前读完全部二十二页。挑选描述你的那一行，按给定顺序阅读其中的页面； 让术语表保持打开。

角色 按此顺序阅读——以及原因
第一个 PR，没时间 1. 从这里开始——第 0 天检查，以及第一个 PR 的八个步骤。2. 准备你的环境——只看已知的宿主机陷阱。3. 克隆、构建与测试——你必须通过的门禁。4. 各个 crate——只看你要改动的那个 crate 的部分。5. 贡献流程——PR 如何被评判。
DevOps 工程师（CI、打包、安装、发布） 1. 从这里开始——配置与规则。2. 准备你的环境——宿主机需要什么，以及看起来像引擎缺陷的陷阱。3. 克隆、构建与测试——安装一个构建版本，把每个 CI 作业当作本地命令，E2E 与混沌测试。4. 项目结构——什么是生成的、CI 检查什么、release.yml 会刷新什么。5. 故障排查——通过消息识别门禁失败。6. 发布与稳定性——版本门禁、推送一个标签会做什么、什么是稳定的。7. 发布文档——发布时会发生什么。8. 环境变量——每一个开关，以及哪些会降低边界。
平台工程师（在引擎接口之上构建） 1. IaaS 与云原生——引擎处于哪一层、它把什么留给控制平面。2. 云原生入门——Kind 与三路协调器。3. 架构——接口（CLI、CRI、管理 API、MCP、节点契约）与各层。4. 各个 crate——delonix-stack、delonix-cri、delonix-mgmt、delonix-mcp。5. 新增一个 Kind——新增一个 Kind 所需的表与协调器接线。6. 系统设计面试——API 的选择及其取舍。7. 云原生标准——什么是合规、部分合规或缺失的，附带日期。
SRE（运维节点、诊断故障） 1. Linux 基础——用一条命令回答"是哪个命名空间、哪个 cgroup、谁持有这个 fd"。2. 准备你的环境——诊断宿主机及其陷阱。3. 故障排查——针对门禁和运行时故障的按症状索引。4. 架构——运行时存在哪些进程、磁盘上的状态、已知限制。5. 系统设计面试——故障模式与单节点的限制。6. 编码约定——退出码意味着什么。7. 环境变量——日志、OTLP 与逃生舱口（escape hatch）。8. 云原生标准——OpenTelemetry 与 Prometheus。
云开发者（Kind、清单（manifest）、镜像、Compose/Docker 兼容性） 1. IaaS 与云原生——这些原则在代码中如何呈现。2. 云原生入门——OCI 镜像与声明式协调。3. 克隆、构建与测试——隔离地构建与运行。4. 各个 crate——delonix-stack 与 delonix-oci。5. Delonixfile 与 VMfile——构建语法。6. 编码约定——Kind 与字段的规则。7. 新增一个 Kind——端到端地把一个 Kind 接入协调器。8. 云原生标准——自有 Kind、Docker API 与 Compose 子集。
Linux 开发者（命名空间、cgroup、网络、虚拟机） 1. Linux 基础——亲手操作各原语。2. 云原生入门——每个原语在代码中位于何处。3. Rust 入门——unsafe、系统调用、多线程进程中的 fork/clone。4. 准备你的环境——AppArmor 与 cgroup 委派（delegation）的陷阱。5. 架构——无根网络基础设施，以及作为序列的两条流程。6. 各个 crate——delonix-linux、delonix-sdn、delonix-vm。7. 构建微虚拟机——KVM、Cloud Hypervisor、libvirt。8. 编码约定——unsafe 与进程的规则。

两项更窄的任务有各自的捷径：改变文档的生成方式从 发布文档开始；配置或隔离一次运行从 隔离引擎的状态开始，然后是 环境变量。
