# __NAME__ (WordPress __TEMPLATE_VERSION__)

A WordPress stack scaffolded by `delonix init -t wordpress -v __TEMPLATE_VERSION__`
— the official `wordpress:__TEMPLATE_VERSION__` PHP-Apache image plus a
**MariaDB** database, with persistent volumes for both and **one** DB password
shared between them. WordPress cannot install without a database, so this is a
**two-service stack**, not a lone container.

## Bring it up

### With Compose (the quick start)

```bash
delonix compose up            # or: docker compose up -d
```

`compose.yaml` runs the **stock** `wordpress:__TEMPLATE_VERSION__` image plus
MariaDB. Open <http://localhost:__PORT__> and you land on the WordPress install
wizard — pick a title, create the admin user, done. The credentials come from
`.env` (generated by `delonix init`, git-ignored); the DB password there feeds
both MariaDB (`MYSQL_PASSWORD`) and WordPress (`WORDPRESS_DB_PASSWORD`).

### With the manifests (baked image + live-reload dev)

**Development** (edit `wp-content/` on the host, WordPress serves it live):

```bash
delonix stack apply -f delonix-manifest.dev.yaml   # stock image, wp-content bind-mounted
```

**Production-shaped** (`wp-content/` baked into your own image):

```bash
delonix build -t __NAME__:dev .                     # bakes wp-content/
delonix stack apply
```

The health probe is `/wp-login.php`.

> Heads-up: a lone `delonix container run wordpress:__TEMPLATE_VERSION__` will
> **not** become healthy — WordPress needs the `db` container from the
> manifest. Always use `delonix compose up` or `delonix stack apply`.

### Set a strong admin password — before exposing the site

WordPress has no factory admin: you create the first user in the install
wizard. Do that (and pick a STRONG password) before the port is reachable by
anyone else — and especially before opening the tunnel below.

## What's in the stack

| Resource | Name | Purpose |
|---|---|---|
| `Network` | `__NAME__-net` | bridge network; WordPress reaches MariaDB by the alias `db` |
| `Volume`  | `__NAME__-dbdata` | MariaDB data (`/var/lib/mysql`) |
| `Volume`  | `__NAME__-wordpress` | WordPress core + bundled content (`/var/www/html`) |
| `Secret`  | `__NAME__-db-credentials` | one secret, both images' own env-var names (`MYSQL_*` for MariaDB, `WORDPRESS_DB_*` for WordPress) |
| `Container` | `__NAME__-db` | `mariadb:11`, alias `db` |
| `Container` | `__NAME__` | WordPress, published on `__PORT__` |

In `compose.yaml` the same two services carry the `wordpress-data` / `db-data`
volumes; the `quality` profile adds SonarQube + its PostgreSQL.

## Custom themes and plugins (`wp-content/`)

`wp-content/plugins/` and `wp-content/themes/` are the seam for YOUR code — one
directory per plugin/theme. WordPress's own bundled content stays in the image
and these are added **on top**, never replacing it:

- **Prod** — the `Delonixfile` `COPY`s them into the image (`delonix build`).
- **Dev** — `delonix-manifest.dev.yaml` bind-mounts them, so a PHP/CSS edit
  shows up on the next request with no rebuild.

| Task | Command |

| Up (compose) | `delonix compose up` |
| Up (dev manifest / prod manifest) | `delonix stack apply -f delonix-manifest.dev.yaml` / `delonix build -t __NAME__:dev . && delonix stack apply` |

## Credentials

`.env` ships with freshly generated random passwords. The manifests'
`__NAME__-db-credentials` secret, by contrast, ships with the placeholder
`wordpress` in cleartext `stringData` — `delonix stack apply` prints a WARNING
about exactly this, on purpose. Before a real deployment, replace it with a
`fromEnvFile: .secrets.env` (kept out of git — see `.dockerignore`) or run
`delonix secret create __NAME__-db-credentials --from-env-file - --force` and
drop `stringData` from the manifest.

## Tests and CI

```bash
find wp-content -type f -name '*.php' -exec php -l {} \;   # syntax gate (CI runs this)
sh scripts/smoke.sh                                        # against a running instance
```

`php -l` is what `.github/workflows/ci.yml` and `.gitlab-ci.yml` both run — a
pure syntax check over the themes/plugins you write under `wp-content/`, no
WordPress runtime and no database. `sonar-project.properties` is ready for a
`sonar-scanner` run; `CONTRIBUTING.md` has the branching model, Conventional
Commits and SemVer.

> Not run in this environment: the CI jobs and `scripts/smoke.sh` need a PHP
> toolchain and a running stack (a container runtime). They are validated
> upstream / in CI, not on the machine that generated this project.

## Quality profile (local SonarQube)

`compose.yaml` ships a `quality` profile with SonarQube and its database, off
by default (they are heavy):

```bash
sudo sysctl -w vm.max_map_count=262144      # once, SonarQube needs it
delonix compose up --profile quality        # or: docker compose --profile quality up -d
```

SonarQube comes up on <http://localhost:9000>; scan with `sonar-scanner` using
`sonar-project.properties`.

## On the internet without a public IP

`delonix-tunnel.yaml` opens an OUTBOUND tunnel: __NAME__ gets an `https`
address on the internet with no public IP, nothing opened on the router, and no
certificate to manage — the provider serves HTTPS with its own. It runs only
when applied; `stack apply` on `delonix-manifest.yaml` does not touch it.
Anyone on the internet can then reach the site.

Finish the install and set a strong admin password first (see above): the
tunnel puts the site — and its `/wp-admin` login — on the internet.

### Just a tunnel (no account, no domain)

1. Install `cloudflared` ([releases](https://github.com/cloudflare/cloudflared/releases),
   or your distribution's package) somewhere on `PATH`.
2. `delonix stack apply -f delonix-tunnel.yaml`
3. `delonix get gateways` — the address is in `PUBLIC URL`.

The address is random (`https://<words>.trycloudflare.com`) and changes every
time the tunnel opens. Close it with `delonix delete gateways __NAME__-tunnel`.

### Your own domain (a stable address)

The domain's DNS has to be on Cloudflare (a free account is enough: point the
domain's name servers, at your registrar, to the two Cloudflare gives you).

1. Cloudflare dashboard → Zero Trust → Networks → Tunnels → **Create a
   tunnel** → Cloudflared. Name it and copy the token (`--token eyJ…`).
2. In the tunnel, add a **public hostname**: `blog.example.org` → service
   `http://localhost:__PORT__`. Cloudflare creates the DNS record.
3. Keep the token in a Delonix secret, typed in so it lands in no file and no
   shell history: run `delonix secret create __NAME__-tunnel --from-env-file -`,
   type `token=<the token>`, then Enter and Ctrl-D.
4. In `delonix-tunnel.yaml`, uncomment `tokenSecretRef` and `hostname`, then
   `delonix stack apply -f delonix-tunnel.yaml`.

Visitors get Cloudflare's certificate for `blog.example.org`. WordPress needs
to know its public URL so it builds links and redirects correctly — set the
Site Address under Settings → General, or define `WP_HOME`/`WP_SITEURL`, to the
`https://` tunnel address once it is stable.

### Other providers

`provider:` also takes:

- `ngrok`: the ngrok agent on `PATH` and an account
  (`ngrok config add-authtoken <token>`). A free account has one fixed name: a
  stable address without a domain of your own. One ngrok tunnel per machine.
- `pinggy`: nothing to install (plain `ssh`), a URL valid for 60 minutes, and a
  warning page shown to browsers before the site.

## Architecture: where to take this

**A rule before the menu: an architecture no test enforces is not an
architecture, it is an intention.** This project ships one — `php -l` over
`wp-content/`, run in CI — and the paths below each say what changes *in that
test*. Grow the code without growing the gate and the discipline is gone within
a few sprints.

### What this project is today

A WordPress deployment, not an application you wrote from scratch: the CMS is
the image, the database and the network are in the manifests/compose file, and
`wp-content/` is where YOUR code goes. The architectural decisions here are
about what belongs in a plugin, what belongs in a theme, and what belongs
OUTSIDE WordPress entirely.

### Path 1 — one plugin per bounded capability

A plugin is already a module boundary with its own lifecycle hooks. Use it: one
plugin per capability (custom post types, an integration, a shortcode library),
activated independently, rather than a pile of `functions.php` edits in the
theme. *The sign you chose wrong:* switching themes loses behaviour that was
never presentational.

### Path 2 — keep the theme presentational

The theme renders; it does not own business rules. Register data and behaviour
in plugins and let the theme consume them. *Patterns:* separation of content
from presentation, child themes for overrides. *The sign you chose wrong:* a
redesign means re-implementing logic.

### Path 3 — heavy or non-CMS work goes beside WordPress

For anything that is not a content concern — a high-traffic public API, a heavy
async job, a data pipeline — put a separate service beside WordPress on the same
Delonix network and talk to it over its API, rather than growing a plugin that
serves the world. *Patterns:* anti-corruption layer, outbox for events leaving
WordPress. **Keep WordPress behind an edge** (`delonix init -t nginx`) before
exposing anything public.

### Choosing

| If your problem is… | Go to | The sign you chose wrong |
|---|---|---|
| "a small feature is spread across the theme" | Path 1 — a plugin owns it | changing themes loses the feature |
| "the theme has business logic in it" | Path 2 — move rules into plugins | a redesign re-implements logic |
| "a request does heavy work the visitor waits for" | Path 3 — a service beside WordPress | page loads stall on a side effect |
| "two integrations keep breaking each other" | one plugin each, public hooks only | a fix in one breaks the other |

### What not to do yet

- **Do not add a plugin because it reads well.** Every plugin is loaded on
  every request; add one when a concrete capability needs its own boundary, not
  before.
- **Do not put business rules in `functions.php`.** They belong in a plugin
  that survives a theme switch.
- **Do not go distributed to get modularity.** A plugin boundary gives you the
  decoupling; a network hop gives you retries, timeouts and a tracing bill.
- **Do not change the architecture and the architecture gate in different
  commits.** They are one change.

## Troubleshooting

- **"Error establishing a database connection"** — MariaDB was not ready when
  WordPress started. `depends_on: condition: service_healthy` (compose) and
  `restart: always` (manifest) mean it recovers on the next start; check
  `delonix container logs __NAME__-db`.
- **The install wizard keeps reappearing** — WordPress stores its state in the
  `__NAME__-wordpress` (compose: `wordpress-data`) volume; a `stack destroy`
  or a removed volume resets it.
- **Your custom theme/plugin does not appear** — in dev it is bind-mounted from
  `wp-content/`; in prod it must be baked in (`delonix build` after adding it).
  Activate it under Appearance → Themes or Plugins.
