# __NAME__

A Next.js __TEMPLATE_VERSION__ application generated by `delonix init -t nextjs`
(App Router, React 19, TypeScript, Node.js 24). It is a small, complete
example — not a skeleton: a page and the backend-for-frontend behind it. One
capability (notes) goes from a form in the browser through Route Handlers to a
use case and a storage port; there are signed webhooks in both directions,
OpenTelemetry traces and metrics, JSON logs, a readiness state that follows
the process lifecycle, and a bounded shutdown.

| | |
|---|---|
| Framework | Next.js `^__TEMPLATE_VERSION__` (App Router, `output: "standalone"`), React 19 |
| Runtime / package manager | Node.js 24 LTS, pnpm (version pinned in `package.json`, provisioned by corepack) |
| UI | a Server Component lists notes, one Client Component is the form |
| API | Route Handlers under `app/api/v1` over a server-only use case |
| Telemetry | OpenTelemetry JS SDK (traces, metrics) registered in `instrumentation.ts` |
| Storage | in memory (`lib/server/memory-note-store.ts`) — replace for real use |
| Contract | `api/openapi.yaml` (OpenAPI 3.1) |

Limits of the example, stated up front: notes live in memory and vanish on
restart, and each replica has its own; the inbound webhook de-duplication and
the pending outbound deliveries are in memory too (see
[docs/adr/0002](docs/adr/0002-webhooks.md)). Nothing here authenticates users
or API callers — add your platform's mechanism before exposing it. This is a
frontend with its BFF, not a general backend: there is no gRPC, and a second
service should not call these Route Handlers as its API.

## Quickstart

Prerequisites: Node.js 24, corepack (ships with Node.js 24), `curl` for the
smoke test; Delonix to build and run the image.

```bash
corepack enable
pnpm install                      # writes pnpm-lock.yaml — commit it (CI requires it)
pnpm dev                          # http://localhost:__PORT__ with reload
pnpm check                        # format check, lint, typecheck, tests, production build
pnpm start &                      # the production server (.next/standalone/server.js)
pnpm smoke                        # health, create/get, 422, 404, the pages → "smoke: OK"
kill %1                           # SIGTERM → ordered shutdown, exit 0
```

`delonix init` does not run a package manager, so a fresh project has no
lock file: the first `pnpm install` resolves the versions, and the lock it
writes is what CI and the image build install from afterwards.

## Layout

```
app/(list)/page.tsx          Server Component: lists notes by calling the use case
app/(list)/note-form.tsx     Client Component: the form, posts to /api/v1/notes
app/(list)/loading.tsx       streaming fallback of the list
app/notes/[id]/page.tsx      one note; calls notFound() for an unknown id
app/error.tsx, not-found.tsx error boundary and 404 page
app/api/v1/**/route.ts       Route Handlers: notes, health, inbound webhook
app/api/[...path]/route.ts   unknown /api paths answer 404 in the API's error shape
instrumentation.ts           register(): runs lib/server/boot.ts once per server process
lib/notes/                   the capability: rules, use cases, ports (NoteStore, NotePublisher)
lib/http/route.ts            transport helpers: request id, error shape, body limits, access log
lib/server/runtime.ts        composition root: builds adapters, hands them to the use cases
lib/server/boot.ts           startup: configuration, telemetry, runtime, signals, readiness
lib/server/shutdown.ts       the ordered shutdown
lib/server/webhooks/         Standard Webhooks signing/verification, outbound dispatcher, dedup
lib/server/{config,logger,telemetry,lifecycle,memory-note-store,traced-notes}.ts
lib/project.ts               the project name and default port `delonix init` wrote
api/openapi.yaml             HTTP contract of the Route Handlers
tests/                       Vitest: everything under `pnpm test`
deploy/otel-collector.yaml   local Collector for development
```

[ARCHITECTURE.md](ARCHITECTURE.md) has the dependency rules, what runs on the
server and what reaches the browser, and a worked example of extending the
capability.

## Configuration

All from the environment, read on the server only and validated when the
server process starts (every problem listed at once, exit code 1 before a
request is handled). See [.env.example](.env.example). `pnpm dev` loads
`.env.local`; `pnpm start` and the image read the process environment.

| Variable | Purpose | Default | Required | Sensitive |
|---|---|---|---|---|
| `APP_ENV` | `development`, `test`, `production` | `development` | no | no |
| `LOG_LEVEL` | `debug`, `info`, `warn`, `error` | `info` | no | no |
| `PORT` / `HOSTNAME` | listen port and address of `pnpm start` | `__PORT__` / `0.0.0.0` | no | no |
| `HTTP_MAX_BODY_BYTES` | request body limit of the notes API | `1048576` | no | no |
| `SHUTDOWN_TIMEOUT` | bound of the shutdown after the drain delay | `15s` | no | no |
| `DRAIN_DELAY` | time serving with readiness at 503 before refusing work | `0s` | no | no |
| `SERVICE_NAME` | service name in logs and telemetry | `__NAME__` | no | no |
| `APP_VERSION` | version in logs and telemetry (the image sets it from `--build-arg VERSION`) | `dev` | no | no |
| `NEXT_MANUAL_SIG_HANDLE` | `true` hands SIGTERM/SIGINT to this service's shutdown; set by `pnpm start` and the image | — | in production | no |
| `WEBHOOK_INBOUND_SECRET` | `whsec_<base64>`; enables the inbound endpoint | — | no | **yes** |
| `WEBHOOK_TARGET_URL` | receiver of `note.created` (https in production) | — | no | no |
| `WEBHOOK_TARGET_SECRET` | `whsec_<base64>`; required with the URL | — | with URL | **yes** |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | OTLP/HTTP collector, e.g. `http://collector:4318` | — (no export) | no | no |
| `OTEL_TRACES_SAMPLER_ARG` | fraction of new traces sampled, `0`–`1` | `1` | no | no |
| `OTEL_SDK_DISABLED` | `true` disables telemetry | — | no | no |

`APP_ENV` is this service's own setting; `NODE_ENV` belongs to Next.js
(`production` under `pnpm start`, `development` under `pnpm dev`). With
`APP_ENV=production` the server refuses to start with an `http://` webhook
target or without `NEXT_MANUAL_SIG_HANDLE=true`.

Secrets come from the environment only, and only server modules read them:
locally from `.env.local` (git-ignored), in Delonix from a secret
(`delonix secret create`, see the manifest comment). No variable here may be
given a `NEXT_PUBLIC_` prefix — Next.js inlines those into the JavaScript it
sends to browsers; `tests/architecture.test.ts` fails if a source file reads one.

## API

Base `http://localhost:__PORT__`. Contract: [api/openapi.yaml](api/openapi.yaml).
Every error has one shape: `{"error":{"code","message","fields"?,"request_id"}}`
with codes `validation_failed` (422), `malformed_json` (400),
`body_too_large` (413), `not_found` (404), `internal` (500), and
`shutting_down` (503, during the last phase of a shutdown).

```bash
curl -si -X POST localhost:__PORT__/api/v1/notes -H 'Content-Type: application/json' \
  -d '{"title":"hello","body":"world"}'
# 201, Location: /api/v1/notes/<id>, {"id":"…","title":"hello","body":"world","created_at":"…"}
curl -s 'localhost:__PORT__/api/v1/notes?offset=0&limit=20'
# {"items":[…],"total":1,"offset":0,"limit":20}
curl -s -X POST localhost:__PORT__/api/v1/notes -H 'Content-Type: application/json' -d '{"title":""}'
# 422 {"error":{"code":"validation_failed","message":"invalid input","fields":{"title":"is required"},"request_id":"…"}}
```

The page at `/` renders the same list on the server by calling the use case
directly (no HTTP hop to its own API); the form posts to `POST /api/v1/notes`
and shows the `fields` of a 422 next to the inputs.

Versioning: breaking changes go to `/api/v2`; `/api/v1` changes are additive.
`tests/openapi.test.ts` fails when the `route.ts` files and the contract drift.

## Webhooks (both directions)

Format: [Standard Webhooks](https://www.standardwebhooks.com) — headers
`webhook-id`, `webhook-timestamp`, `webhook-signature: v1,<base64 HMAC-SHA256>`
over `<id>.<timestamp>.<raw body>`.

- **Inbound** `POST /api/v1/webhooks/inbound` (404 without
  `WEBHOOK_INBOUND_SECRET`): the Route Handler reads the raw bytes and
  verifies the signature before parsing anything, refuses timestamps more
  than 5 minutes off (replay window), compares in constant time, acknowledges
  a repeated `webhook-id` without processing it again, and limits the body to
  256 KiB. Events: `ping`, `note.create` (runs the same use case as the API).
- **Outbound** (only with `WEBHOOK_TARGET_URL`): each created note is sent as
  `note.created` from the server, after the response (`after()` from
  `next/server`), with `webhook-id` = note id (the receiver's idempotency
  key), a 5 s timeout per attempt, and up to 4 attempts with exponential
  backoff and full jitter on network errors, 429 and 5xx; other answers are
  final. Deliveries are counted in the `webhook.deliveries{outcome}` metric
  and logged.
- **Delivery semantics**: at-least-once while the process lives; deliveries
  pending at shutdown are awaited within `SHUTDOWN_TIMEOUT`, what remains is
  lost; more than 100 pending drops and counts. Never exactly-once. For
  durable delivery, see [docs/adr/0002](docs/adr/0002-webhooks.md).

Sign a test delivery by hand:

```bash
SECRET=whsec_$(head -c 32 /dev/urandom | base64); export WEBHOOK_INBOUND_SECRET=$SECRET
# restart the server with that variable, then:
ID=msg_1; TS=$(date +%s); BODY='{"type":"ping"}'
KEY=$(printf %s "${SECRET#whsec_}" | base64 -d | xxd -p -c 256)
SIG=$(printf '%s.%s.%s' "$ID" "$TS" "$BODY" | openssl dgst -sha256 -mac HMAC -macopt hexkey:$KEY -binary | base64)
curl -si -X POST localhost:__PORT__/api/v1/webhooks/inbound -H "webhook-id: $ID" \
  -H "webhook-timestamp: $TS" -H "webhook-signature: v1,$SIG" -d "$BODY"   # 204
```

## Logs, traces, metrics

- Logs: JSON on stdout, one line per event, with `service`, `version`,
  `environment`, `request_id`, and `trace_id`/`span_id` inside a request.
  Keys containing `authorization`, `cookie`, `password`, `secret`, `token`,
  `signature` or `api_key` are replaced by `[REDACTED]`. Query strings,
  headers and bodies are never logged. Health probes log at `debug`. The
  startup banner Next.js prints (`▲ Next.js …`, `✓ Ready`) is plain text and
  not under this project's control.
- Traces: Next.js opens the request span (`POST /api/v1/notes`) and its own
  children; this project adds `notes.*` for the use case, and
  `webhook.deliver` with one `POST` client span per attempt, sent with a
  `traceparent` header — so the outbound call and its log lines share the
  request's trace id although they run after the response. Health probes are
  not traced.
- Metrics: `webhook.deliveries`. Next.js does not emit HTTP server metrics.
- Without `OTEL_EXPORTER_OTLP_ENDPOINT` nothing is exported, but trace ids
  still appear in logs. A collector that is down costs dropped batches, not
  requests, and at most 3 s at shutdown. Maturity: traces and metrics are
  stable in the OpenTelemetry JS SDK; logs go to stdout, not through the OTel
  logs API.

Local collector: [docs/runbooks/operations.md](docs/runbooks/operations.md#observability).

## Lifecycle

`/api/v1/health/live` answers 200 while the process runs.
`/api/v1/health/ready` is 503 `starting` until startup finished, 200 `ready`,
and 503 `draining` from the first SIGTERM/SIGINT. Next.js does not route a
request before `instrumentation.ts` has finished, so `starting` is not
normally observed from outside.

Shutdown, with `NEXT_MANUAL_SIG_HANDLE=true` (what `pnpm start` and the image
set): readiness 503 → `DRAIN_DELAY`, still serving → new API requests answered
503 `shutting_down` → requests and page renders in flight finish → pending
webhooks drain → telemetry flushes → exit 0. Everything after the drain delay
shares `SHUTDOWN_TIMEOUT`; exit 1 when the deadline cut a step short; a second
signal exits at once. Without that variable Next.js handles the signal itself:
it closes the listener immediately, waits for requests in flight without a
deadline and exits 143 — no drain window, no telemetry flush. Why, and what
this design cannot do, is in [docs/adr/0003](docs/adr/0003-shutdown.md). No
persistence, so no migrations.

## Build and deploy with Delonix

```bash
delonix build -t __NAME__:dev .       # two stages; .dockerignore is honoured
delonix stack apply                   # delonix-manifest.yaml
curl localhost:__PORT__/api/v1/health/ready
delonix stack destroy                 # removes what the manifest created
```

The image holds `.next/standalone` only (server, traced production
dependencies, browser assets). The manifest publishes `__PORT__`, sets
`APP_ENV=production`, 512M/1 CPU, a read-only root filesystem with a `/tmp`
tmpfs, and `restart: always`.
The image runs as the unprivileged user `node` (uid 1000), which owns nothing
in the image. The manifest names it (`user:`) because the engine applies an
image's USER only when asked — see
[docs/adr/0004](docs/adr/0004-container-image.md). Other engines can build the
`Delonixfile` as a Dockerfile.

## Tests and CI

`pnpm test` (Vitest) runs: use-case tests; the Route Handlers called directly
with a `Request` (happy path, every error class, pagination, body limit,
readiness transitions, the in-flight count); webhook signature, replay and
duplicate tests; dispatcher retry/backoff/drop tests; the shutdown sequence;
the one-trace test (request → use case → outbound call → log lines); the
OpenAPI drift test and the architecture test. `pnpm smoke:production` then
runs the built server for real. CI (`.github/workflows/ci.yml`,
`.gitlab-ci.yml`) runs `pnpm check`, `pnpm smoke:production` and the audit,
with a read-only token and actions pinned by SHA; it fails with a message when
`pnpm-lock.yaml` is not committed. Dependabot updates npm packages, actions
and the base image. There are no browser tests: the form is exercised by hand.

## Supported versions

`delonix init -t nextjs -v 15` or `-v 16` (default). Both use React 19 and
Node.js 24; Next.js 14 is not offered (it peers on React 18). On the first
`pnpm build` or `pnpm typecheck` Next.js adjusts `tsconfig.json` for its
major — the shipped file is the Next.js 16 form; Next.js 15 sets `jsx` back to
`preserve`. Commit the result.

## Troubleshooting

| Symptom | Cause |
|---|---|
| CI: `pnpm-lock.yaml is missing` | run `pnpm install` once and commit the lock |
| exits with `fatal: configuration:` and a list | an invalid variable — the message names each |
| `NEXT_MANUAL_SIG_HANDLE: must be true in production` | started with `next start` or `node server.js` directly; use `pnpm start`, the image, or set the variable |
| inbound webhook answers 401 | wrong secret, body re-encoded by a proxy, or clock skew over 5 minutes |
| `/api/v1/webhooks/inbound` is 404 | `WEBHOOK_INBOUND_SECRET` is not set |
| the page has no styles under `node .next/standalone/server.js` | `.next/static` was not copied; `pnpm build` does it (`scripts/copy-static.mjs`) |
| the container is unreachable from outside | `HOSTNAME` was overridden by the runtime; it must be `0.0.0.0` |
| no traces in the collector | `OTEL_EXPORTER_OTLP_ENDPOINT` unset, or not the `:4318` HTTP port |
